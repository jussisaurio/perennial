# Brief for agents

Every agent reads this first, along with CLAUDE.md. Your prompt gives the task: the issue, the time box, and anything special. This file gives the rest, so prompts stay short.

## Setup
- **Make your own worktree first.** You start in the owner's checkout, and other agents work there too: never edit files, commit or switch branches in it. Run this once, with a short name for your task (lowercase letters, digits and dashes, such as `stile-982`):
  `git fetch -q origin main && bash -c "$(git show origin/main:scripts/agent-worktree.sh)" agent-worktree <name>`
  This runs main's copy of `scripts/agent-worktree.sh`, because the owner's checkout may be old. It makes the branch `<name>` from origin/main and a worktree for it at `.claude/worktrees/<name>`, installs the packages, and makes your scratch folder. It prints both paths. The autorun agent in GitHub Actions works alone, so it skips this step.
- **Run every command in your worktree.** Each Bash call starts in the owner's checkout, so begin each call with `cd <worktree> && `, or use `git -C <worktree>`. Give Edit and Write the worktree's absolute paths. The shell has no extra limits: heredocs, `$(...)`, variables, loops, pipes and `&&` chains all work.
- **Commit and open the PR** with a message file or a heredoc: `cd <worktree> && git commit -F <message file>`, then `cd <worktree> && git push -q origin HEAD && gh pr create --title "..." --body-file <body file>`.
- Other agents merge in parallel: if your PR conflicts, rebase onto origin/main, re-run your checks and force-push with lease (`git push --force-with-lease origin HEAD`).
- **Scratch files:** in your scratch folder, `.scratch/<name>/` in the owner's checkout. It is gitignored, and it stays when your worktree is removed. Keep files that matter there (story-loop answers, reports), not in /private/tmp: macOS empties /private/tmp.
- **E2E runs:** run them the normal way (`bunx playwright test e2e/x.spec.ts` in web/). Your worktree's name gives the run its own ports and its own database (`web/e2e/worktree.ts`); the database is made on the first run. At most 3 runs go at once on the machine. A 4th waits for a free slot and prints a line that says so; this is normal. If a port is still in use, the run fails loudly at start: set `E2E_PORT_OFFSET` to another multiple of 10.
- **To wait for something,** use Monitor, not `sleep`.
- **Postgres** is one shared container (`docker compose up -d` from the owner's checkout). Never touch the `pg-sandbox` container.
- Run only the specs you need, not the whole suite.

## Pick an issue
- **With no task in your prompt,** take the issue that `bun scripts/autorun/run.ts next` prints: the open `ready` issue with no live claim and the highest priority (P0 first), oldest first. The alarm issue comes before all others. `tracking` and `needs-owner` issues are never `ready`.
- **Claim it before you start,** so that no other agent takes it, local or in the autorun: `bun scripts/autorun/run.ts claim <n>`. It comments on the issue, or refuses if another agent holds it. A claim ends by itself after 3 hours: on a longer task, run `claim <n>` again to renew it. If the issue stays open when you stop, run `bun scripts/autorun/run.ts release <n>` and comment what is left.
- **Label each issue you file:** one of P0–P3, and `ready` (it says what to change and how to check it), `needs-owner` (a comment gives the owner's exact step) or `tracking` (it only tracks other issues). Sentry files issues with no labels: the first agent that sees one adds them.

## Checks
- **Light testing:** before merging, run `bun run check` at the root. It is one command for everything except e2e: the typecheck (every workspace; in web/ it covers the unit tests, the e2e files and the Playwright configs too), lint, knip (unused files, exports and dependencies), the full web unit suite (about 5 s; a test can pass alone and fail beside the others, #661), the tests of every folder in scripts/, and the server tests. It takes about 20 s (10 s without the server tests). It prints one line per step, runs every step even after a failure, prints the output of the failed steps and exits non-zero if any failed. The server tests need Postgres: if it is not up, that line says `skip`, so start it (`docker compose up -d` from the main checkout) when you changed server/ or contract/. CI runs the same command. Also run the e2e specs closest to your change. A test for a fix must fail without the fix.
- **A check decides by its own exit code.** Do not pipe a check into `tail` or `grep` and then chain `&& git commit`: the pipe returns the last command's status, so a failed check still commits (this happened on PR #191).
- Never run prettier (there is no config, and it rewraps files).
- Pin the clock and viewport in tests that depend on them.
- **UI changes:** before merging, take screenshots on phone and desktop, light and dark, and look at them yourself. That look is the whole check: no other agent reviews them. The app must look like a premium app: nothing misaligned or cheap-looking, sibling buttons of equal width, an even rhythm of spacing, and one clear main action (#620 shipped without this look). Use the screenshot script, not a spec of your own. In web/: `SHOTS_DIR=<your scratch folder> bun run shots -g "today|shed"`. It names its screens in `web/e2e/shots.ts` and its garden spots in `web/e2e/spots.ts`. Add yours there if it is not in the list. For each app screen the script also checks the page for faults that need no taste (`web/e2e/uiFaults.ts`): text cut off or out of its box, a thing partly off the screen, a page that scrolls sideways, two controls on top of each other, a tap target under 24 px, and axe's WCAG rules. It prints one line per fault (screen, rule, element, box) and fails. Fix the fault. Never add an element to an ignore list: if the check is wrong, change its rule and say why in a comment. `e2e/ui-faults.spec.ts` runs the same check in CI's e2e job on `main`. It is not in the required fast job, because it needs a browser. Garden spots are not checked yet (#1008). Run it in the background and wait with Monitor: it may wait for an e2e slot. Shed notes need 60+ known words, so garden spots use `/?demo=es:800` (it also opens the way over the stile, note n08 at 486 known words).
- **To see and use the running app, use the look tool**, not a spec of your own. In web/: `bun run look <your scratch folder> --demo es:800 --spot walk "hold w 3" "tap stile" "wait mode free"`. It opens the app at a demo level (and a garden spot from `web/e2e/spots.ts`, a time of day, phone or desktop, light or dark), runs your steps, and after each step writes a picture and a JSON file. The JSON has the state: where you stand, the walker's mode, what is in reach, the action button's name, the scenery and labels in view with their boxes on the page, the buttons, the text and the console errors. Run `bun run look` with nothing after it for the full list of steps. Read the JSON first; open a picture when you need to see how it looks. Like the shots, it may wait for an e2e slot.
- **The two garden gates below are only for a new way to move or interact in the garden** (a new verb, a new place to walk, a new thing that moves you or the visitors). A small change skips both: one element, copy, art, or a tweak to an interaction that exists. It still updates its section and claims in docs/garden-play.md. If you are not sure, ask: could this surprise a player about where they can go or what a button does? If not, skip. #976 back-tests these agent judges on problems the owner found. By its numbers each gate is kept, changed or dropped.
- **Play description review (a new way to move or interact, before you build):** write or update the feature's section in docs/garden-play.md. Write it in prose, as the learner meets it: what they see, how they can tell what to do, each thing they can do and what happens, and what they can't do and how they can tell. Then start one fresh Opus agent as the reviewer and wait for it. It gets only that section, the rest of garden-play.md and CLAUDE.md's product rules. It looks for friction: anything a first-time player would not guess, a button that moves you, a thing that looks possible but isn't (or the reverse), an outcome that seems arbitrary, a rule that differs from a nearby feature, and steps that exist only for the code's sake. Change the design until it finds nothing serious. The text goes in your PR, with its claims and one e2e test per claim (see garden-play.md, "The text becomes the tests").
- **Playtest (a new way to move or interact):** after your own checks, start one fresh Opus agent as the playtester and wait for it. It gets only the issue, the PR and the feature's section in docs/garden-play.md, not your reasoning. It also checks that the build plays the way the text says. It plays the change the way the learner would: with the look tool (above) at the right `--demo` level, by holding keys (WASD and arrows) and clicking the action button, and it looks at the picture after each step. It checks: Can I tell what I can and can't do, just from looking? Can I walk everywhere that looks walkable, and never through anything solid? Does anything move me without me walking (a teleport, an auto-walk, a snap back)? Does anything else vanish and show up somewhere else, or do the visitors walk or fly where they go? Does every button do what its label says, to a thing in reach? What feels cheap, odd or arbitrary? It reports with the pictures. Fix everything it finds before you merge. If you can't fix something, file it and say so in the PR.
- **Story text or pacing** (notes, thoughts, frog lines, their thresholds): follow [story-loop.md](story-loop.md). New lines are drafted in English, adapted and shipped; the owner may rewrite them later. A line the owner wrote is only changed by a proposal to the owner.
- **Garden tests wait on the game, not the clock:** CI's software WebGL draws about 7 frames a second (#793). Hold keys and wait in game seconds or on game state (position, yaw), never fixed wall-clock times, or a test that passes locally fails on CI.
- **A test red on main:** first find the last green main run and the first red one, and look at the merges in between (`gh run list --branch main --workflow CI`). That finds the cause faster than guessing (#796).
- **Machine load:** e2e runs are queued, so load from them stays near the core count. If an e2e test still times out, run `uptime` and rerun only that spec with `--workers=1`. If it fails alone, it's a real failure: fix it. If it fails only under load, say so in the PR. Never just rerun it until it's green.
- **Perf runs:** do not run `bun perf/ui.ts` while any e2e run is going on the machine. The extra load changes the numbers.

## PR and merge
- One PR does one thing. It says `Closes #n`, or `Refs #n` when it is one part of an issue.
- **Some tasks need no code change:** the bug is already gone, or the issue is wrong. Then close the issue yourself (`gh issue close <n> --comment "..."`), with a comment that gives the evidence, and open no PR. The owner allows agents to close issues.
- Commits end with the `Co-Authored-By` line your session gives you.
- **The repo is public.** No secrets, personal data or steps to exploit a bug in commits, issues, PRs or comments. Describe a security problem as a class, and fix it before you write the details.
- The PR body ends with `Reviewed: <none | playtest>`, a blank line, then `🤖 Generated with [Claude Code](https://claude.com/claude-code)`.
- Merge right after your checks: `scripts/merge.sh <pr>`. It works from any worktree, and it always runs main's copy of itself. `main` has two required checks: the CI jobs "Typecheck, lint, unit tests, build" and "Decks (schema, up to date, compatibility, replay)". The script asks GitHub to merge the PR when both pass, waits (about a minute), and deletes the remote branch. The PR is merged only if the last line says `MERGED`. If a required check fails, the script prints `NOT merged`, the check's name and a link, and exits non-zero: fix the PR, push, and run the script again. The e2e tests are not required: they run on `main` after the merge.
- **Migrations are expand, then contract:** never drop a table or column in the same release that stops using it. Railway runs migrations while the old version is still serving. #604 broke this rule and caused #614. The full rule is in [DEPLOY.md](DEPLOY.md).

## Scope and decisions
- **Do the one or two things that matter most, merge, and stop.** Smaller leftovers become issues, with their numbers. If you stop early but found a likely cause, file it at once so another agent can start (six agents that polished small wins used up the usage limit in an hour).
- **Decide, don't ask** (CLAUDE.md, "You decide"). To pick a tool or vendor, take the one that is well regarded, say its main risk in one line, and build. No surveys or bake-offs (#305), unless it is about money, data or security.
- **When you cut or change a thing, look for what it leaves without a purpose.** The stick had no use once fetch was cut (#835).
- **Never wait in the foreground** for CI, an agent or a run longer than about 30 s. Start it in the background and do other work until it reports.
- **Runs with nobody watching:** `.github/workflows/autorun.yml` starts a few agents in GitHub Actions, each on its own issue by the pick rule. It is off until the owner turns it on. [autonomy.md](autonomy.md) says how a run goes and what it trusts.
- **An automatic judge is checked before it drives work.** Compare a sample of its verdicts with the owner's or a person's first. An LLM judge of the audio clips failed good clips and missed bad ones (#776), so a clip is re-made only when a person reports it.
- **Check the sim against real use.** The sim learner and the story's agent readers only check themselves. Before you tune FSRS, retention, pacing or when the story comes, run `bun run real-use` and read [real-use.md](real-use.md), "How to use the numbers".

## When you start other agents
- Start parallel agents for work that splits cleanly. A bug that comes in while you work on something else goes to an agent, not to you.
- **Start them without `isolation: worktree`.** Its shell check refuses heredocs, `$(...)`, loops and git chains, and it can't be turned off (#982). Each agent makes its own worktree as its first step (Setup, above).
- The first line of the prompt names the issue or request the task serves. An agent that could not tell whose task it had once stopped a whole deck batch.
- The prompt gives the task, a time box and a name for the agent's worktree, unique among the agents you run. This file gives the rest.
- Judging work (a play review, a playtest, proofreading, story readers and judges) runs on the strongest model your session can start. Where a doc says "Opus", it means that. Mechanical work (renames, applying exact fix notes, link checks) can use a cheaper model.
- Before you start a follow-up, check that no running or just-finished agent already has it.
- An agent's report is a claim, not a source. If you pass it on, say "the agent reports", and check what you can.

## Report
Your final message gives:
- the PR number, or the issue you closed;
- what changed, for the learner or the owner;
- anything left for later, filed as issues;
- **A source for every fact:** `file:line`, a command's output or a URL. If you did not check it, check it now, or say plainly that it is a guess;
- **Friction:** a few bullets on what was annoying or slow, and what would have made it easier (tools, repo setup, docs, the prompt). These go to #656.
- **Least sure about:** one thing that you could not check. If you can check it, check it instead.
