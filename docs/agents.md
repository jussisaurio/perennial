# Brief for agents

Every agent reads this first, along with CLAUDE.md. Your prompt gives the task: the issue, the time box, and anything special. This file gives the rest, so prompts stay short.

## Setup
- Branch from an up-to-date `origin/main`. Other agents merge in parallel: if your PR conflicts, rebase onto origin/main, re-run your checks and force-push with lease.
- **A new worktree has no packages:** run `bun install` at the root and in `web/` before any check.
- **Scratch files:** in the session scratchpad your prompt names, under a subfolder named after your task. Never at its top level, because other agents share it.
- **E2E runs:** run them the normal way (`bunx playwright test e2e/x.spec.ts` in web/). In a worktree under `.claude/worktrees/`, the worktree's name gives the run its own ports and its own database (`web/e2e/worktree.ts`); the database is made on the first run. At most 3 runs go at once on the machine. A 4th waits for a free slot and prints a line that says so; this is normal. If a port is still in use, the run fails loudly at start: set `E2E_PORT_OFFSET` to another multiple of 10.
- **Shell commands:** in a worktree, a guard blocks compound commands: `$(...)`, `$VAR` arguments, `for` loops, `&&` chains with git, and process tools like `pgrep`, `lsof` and `pkill`. Run one plain command per call; for git, use `git -C <absolute worktree path> ...` (not a relative path like `..`) instead of `cd ... && git`. For anything longer, write a small script in your scratch folder and run that. To wait for something, use Monitor, not `sleep`.
- **Postgres** is one shared container (`docker compose up -d` from the main checkout). Never touch the `pg-sandbox` container.
- Run only the specs you need, not the whole suite.

## Checks
- **Light testing:** before merging, run `bun run check` at the root. It is one command for everything except e2e: the typecheck (every workspace), lint, knip (unused files, exports and dependencies), the full web unit suite (about 5 s; a test can pass alone and fail beside the others, #661), the tests of scripts/ (deck, tts, alarm), and the server tests. It takes about 20 s (10 s without the server tests). It prints one line per step, runs every step even after a failure, prints the output of the failed steps and exits non-zero if any failed. The server tests need Postgres: if it is not up, that line says `skip`, so start it (`docker compose up -d` from the main checkout) when you changed server/ or contract/. CI runs the same command. Also run the e2e specs closest to your change. A test for a fix must fail without the fix.
- Never run prettier (there is no config, and it rewraps files).
- Pin the clock and viewport in tests that depend on them.
- **UI changes:** before merging, take screenshots on phone and desktop, light and dark, and look at them yourself. Nothing misaligned or cheap-looking. Use the screenshot script, not a spec of your own. In web/: `SHOTS_DIR=<your scratch folder> bun run shots -g "today|shed"`. It names its screens and garden spots in `web/e2e/shots.ts`. Add a screen there if yours is not in the list. Run it in the background and wait with Monitor: it may wait for an e2e slot. Shed notes need 60+ known words, so garden spots use `/?demo=es:800` (it also opens the way over the stile, note n08 at 486 known words).
- **Play description review (garden movement or interaction, before you build):** write or update the feature's section in docs/garden-play.md. Write it in prose, as the learner meets it: what they see, how they can tell what to do, each thing they can do and what happens, and what they can't do and how they can tell. Then start one fresh Opus agent as the reviewer and wait for it. It gets only that section, the rest of garden-play.md and CLAUDE.md's product rules. It looks for friction: anything a first-time player would not guess, a button that moves you, a thing that looks possible but isn't (or the reverse), an outcome that seems arbitrary, a rule that differs from a nearby feature, and steps that exist only for the code's sake. Change the design until it finds nothing serious. The text goes in your PR, with its claims and one e2e test per claim (see garden-play.md, "The text becomes the tests").
- **Playtest (garden movement or interaction):** after your own checks, start one fresh Opus agent as the playtester and wait for it. It gets only the issue, the PR and the feature's section in docs/garden-play.md, not your reasoning. It also checks that the build plays the way the text says. It plays the change the way the learner would: in a Playwright browser at the right `?demo=` level, with the keyboard only (WASD and arrows, the action key), recording video (`video: "on"`) and looking at frames from it. It checks: Can I tell what I can and can't do, just from looking? Can I walk everywhere that looks walkable, and never through anything solid? Does anything move me without me walking (a teleport, an auto-walk, a snap back)? Does anything else vanish and show up somewhere else, or do the visitors walk or fly where they go? Does every button do what its label says, to a thing in reach? What feels cheap, odd or arbitrary? It reports with frames. Fix everything it finds before you merge. If you can't fix something, file it and say so in the PR.
- **Story text or pacing** (notes, thoughts, frog lines, their thresholds): follow [story-loop.md](story-loop.md). New lines are drafted in English for the owner first.
- **Garden tests wait on the game, not the clock:** CI's software WebGL draws about 7 frames a second (#793). Hold keys and wait in game seconds or on game state (position, yaw), never fixed wall-clock times, or a test that passes locally fails on CI.
- **A test red on main:** first find the last green main run and the first red one, and look at the merges in between (`gh run list --branch main --workflow CI`). That finds the cause faster than guessing (#796).
- **Machine load:** e2e runs are queued, so load from them stays near the core count. If an e2e test still times out, run `uptime` and rerun only that spec with `--workers=1`. If it fails alone, it's a real failure: fix it. If it fails only under load, say so in the PR. Never just rerun it until it's green.
- **Perf runs:** do not run `bun perf/ui.ts` while any e2e run is going on the machine. The extra load changes the numbers.

## PR and merge
- One PR does one thing. It says `Closes #n`, or `Refs #n` when it is one part of an issue.
- **Some tasks need no code change:** the bug is already gone, or the issue is wrong. Then close the issue yourself (`gh issue close <n> --comment "..."`), with a comment that gives the evidence, and open no PR. The owner allows agents to close issues.
- Commits end with `Co-Authored-By: Claude Opus 5.5 (1M context) <noreply@anthropic.com>`.
- The PR body ends with `Reviewed: <none | quick | playtest>`, a blank line, then `🤖 Generated with [Claude Code](https://claude.com/claude-code)`.
- Merge right after your checks: `scripts/merge.sh <pr>`. It works from any worktree. `main` has two required checks: the CI jobs "Typecheck, lint, unit tests, build" and "Decks (schema, up to date, compatibility, replay)". The script asks GitHub to merge the PR when both pass, waits (about a minute), and deletes the remote branch. The PR is merged only if the last line says `MERGED`. If a required check fails, the script prints `NOT merged`, the check's name and a link, and exits non-zero: fix the PR, push, and run the script again. The e2e tests are not required: they run on `main` after the merge.
- **Migrations are expand, then contract:** never drop a table or column in the same release that stops using it. Railway runs migrations while the old version is still serving. #604 broke this rule and caused #614. The full rule is in [DEPLOY.md](DEPLOY.md).

## Report
Your final message gives:
- the PR number, or the issue you closed;
- what changed, for the learner or the owner;
- anything left for later, filed as issues;
- **Friction:** a few bullets on what was annoying or slow, and what would have made it easier (tools, repo setup, docs, the prompt). These go to #656.
- **Least sure about:** one thing.
